# Preregistration: Qwen3.6-35B-A3B on small Apple Silicon Macs

Date: 2026-07-14

This file fixes the target, release scope, measurements, and stop conditions
before the Qwen implementation starts.  Explanations of model mechanics and
cache lifetime belong beside the implementation, as required by `AGENT.md`.

## Decision

Add one text model: **Qwen3.6-35B-A3B**, GGUF architecture `qwen35moe`.

The initial release target is Metal on Apple Silicon with 16 GiB or more unified
memory.  It must support resident inference when the model fits and explicit SSD
streaming of complete routed experts when it does not.

Do not add Qwen3-Coder-Next as an alias or variant.  It is a different 80B,
512-expert, top-10 architecture and its Q4_K_M GGUF is about 48.4 GB.  The
general Qwen3.6 model already has stronger published agentic-coding scores and
requires less than half the model I/O.

Do not add Qwen3.6-27B to the first release.  Its published coding scores are
higher, but all 27B dense parameters are active for every token.  A 16 GiB Mac
cannot safely keep its roughly 18 GB Q4_K_M model plus runtime state resident;
streaming the missing dense weights on every token defeats ds4's routed-expert
cache design.

Qwen3.7-Max and Qwen3.7-Plus are API-only as of this date.  There are no
official downloadable weights or GGUFs to support.  Do not speculate about
their architecture.  Keep the Qwen family boundary narrow enough that a future
open release can reuse it only if its metadata and tensor layout actually
match.

## Fixed model geometry

Validate these values from GGUF metadata rather than silently overriding them:

- 40 transformer blocks: 30 Gated DeltaNet linear-attention blocks and 10 full
  attention blocks in a 3:1 pattern.
- Hidden size 2048; 16 query heads, 2 KV heads, head dimension 256.
- 256 routed experts per block, top 8 per token.
- Routed and shared expert intermediate size 512.
- Native context 262,144; the first small-Mac release is qualified at 8,192 and
  32,768 tokens, not automatically at the architecture maximum.
- Vocabulary 248,320, Qwen3.5 pre-tokenizer, canonical Qwen3.6 chat template.
- One auxiliary MTP block exists in the published checkpoint.

MTP is excluded from the first release.  A Metal report on an M1 Pro 32 GB
measured 26.23 t/s without MTP and 1.93 t/s with the experimental self-MTP
path.  The release path must remain ordinary autoregressive decoding until an
A/B test on ds4 shows a real win:
<https://github.com/ggml-org/llama.cpp/issues/23011>.

## Blessed GGUF recipe

The first release supports one ds4-built quantization recipe, not every
community GGUF carrying the same architecture name:

- routed expert gate, up, and down matrices: Q4_K;
- large non-routed projection matrices: Q8_0 where an existing ds4 kernel
  supports it, otherwise F16 for the first correctness build;
- normalization weights, router logits, shared-expert gates, and Gated
  DeltaNet control/state parameters (`ssm_a`, alpha, beta, convolution, time
  step, and state norm): F32 in the first correctness build;
- embeddings and output head: Q8_0 or F16, selected once by measured NLL and
  memory rather than by file-size preference;
- no vision tower and no MTP block in the runtime artifact.

The stock Q4_K_M mixture includes tensor types that ds4 does not currently
execute on every required path.  A purpose-built layout keeps the release
surface small and reuses the existing validated Q4_K expert kernels.  The
llama.cpp quantizer supports regex tensor-type overrides, so a separate generic
quantization framework is not required.

### Prebuilt-input amendment

This amendment was recorded before transforming or testing the release
artifact.  The input is the prebuilt
`unsloth/Qwen3.6-35B-A3B-GGUF` `UD-Q4_K_S` file at revision
`a483e9e6cbd595906af30beda3187c2663a1118c`, rather than a local conversion of
the 67 GiB official BF16 checkpoint.  Its exact size is 20,893,015,008 bytes
and its expected LFS SHA-256 is
`a8138f183e3993f12cdc23afd2babb8cdb084e64088ce4a256d49101d47b949c`.

The source is already text-only, excludes MTP, and has the required 733-tensor
shape.  Of those tensors, 729 already have the blessed ds4 types and must be
copied without requantization.  The only payload conversions are:

- `blk.34.ffn_down_exps.weight`, `blk.38.ffn_down_exps.weight`, and
  `blk.39.ffn_down_exps.weight`: Q6_K to Q4_K, so every routed expert has the
  same cache-slab layout;
- `output.weight`: Q6_K to Q8_0, matching the validated dense output path.

The expected final histogram is F32=361, Q8_0=252, Q4_K=120, Q6_K=0.  The
Unsloth file also has `tokenizer.ggml.padding_token_id=248055` and a modified
8,057-byte chat template.  Before quantization, a pinned llama.cpp metadata
rewrite must restore padding ID 248044 and the official 7,764-byte template
whose SHA-256 is
`e84f32a23fdda27689f868aa4a1a5621f41133e51a48d7f3efcbea2839574259`.
The loader contract is not relaxed to accept either community value.

This shortcut changes the original no-requantization assumption for three of
the 120 routed tensor banks.  It is accepted only if all of the following
hold:

1. the source passes its full LFS SHA-256 before either rewrite starts;
2. the dry-run and final tensor inventories prove that exactly those four
   tensors changed type and that all 729 remaining tensor payloads are
   byte-identical to the source;
3. the normalized model is scored against the unchanged Unsloth source on the
   same pinned Qwen continuation/logit set; an average NLL regression above
   0.02 nats/token or top-1 disagreement above 2% at the measured positions
   rejects the shortcut;
4. DS4 and pinned llama.cpp agree on greedy tokens and meet the complete
   end-to-end logits tolerances below using the normalized file.

If the quality gate rejects the three Q6_K-to-Q4_K conversions, the fallback
is the original BF16-to-blessed-layout route or explicit Q6_K runtime support;
the thresholds are not loosened after seeing the result.

Each Q4_K routed expert contains three 2048 x 512 matrices and occupies exactly
1,769,472 bytes (1.6875 MiB) with the current Q4_K block layout.  The 40 x 256
expert bank has 10,240 cacheable expert instances.  A 4-7 GiB expert cache on a
16 GiB machine would hold roughly 2,427-4,247 instances, or 24-41% of the bank.
That cache range is an engineering estimate until non-routed residency and
Metal scratch are measured from the actual GGUF.

## Architecture and reuse boundary

Reuse without semantic changes:

- mmap GGUF parser and metadata access;
- explicit `pread`-based expert cache, memory locking, AUTO residency planning,
  hot preload, cache telemetry, and fail-closed memory policy;
- Q4_K routed-expert Metal matvec kernels, shared-expert overlap machinery, and
  sampling primitives;
- HTTP transport, OpenAI/Anthropic request plumbing, session ownership, and KV
  checkpoint infrastructure;
- existing model-free, build-isolation, SSD residency, and server tests.

Add behind a model-family boundary:

- `qwen35moe` metadata validation and tensor binding;
- a Qwen tokenizer pre-split path and special-token IDs loaded from metadata;
- Qwen chat rendering, thinking controls, XML tool-call parsing, and tool
  response rendering;
- Gated DeltaNet convolution, recurrent state, decay/beta update, gated RMSNorm,
  and chunked-prefill kernels;
- gated full attention with partial split-half (NeoX) RoPE;
- top-8 routing and shared-expert sigmoid gating;
- per-layer recurrent-state session serialization and exact prefix reuse.

Do not merge the GLM branch wholesale.  Its model-family separation and
shape-driven binding are useful design references, but Qwen's attention and
recurrent state are different and must have their own small implementation.

## Implementation tranches and estimate

The estimates are engineering days for one developer familiar with ds4 and
include the named verification work.

1. Loader, shape boundary, tokenizer/template fixtures, reference-vector
   collector: 4-6 days.
2. CPU/reference Qwen graph and deterministic token/logit agreement: 6-9 days.
3. Metal resident Gated DeltaNet, full attention, and top-8 MoE: 8-12 days.
4. SSD expert streaming, overlap, AUTO budget, and 16 GiB hardening: 6-9 days.
5. Server/tool calling, session checkpoints, long-context and coding quality:
   4-7 days.
6. Quant recipe, regression A/Bs, documentation, and review cleanup: 3-5 days.

Expected total for an upstream-quality Apple/Metal release: **31-48 engineering
days (about 6-10 full-time weeks)**.  A first correct resident token path is
plausible in 10-15 days.  CUDA and ROCm production parity are outside this
estimate and would add approximately 15-25 days plus access to the hardware.

The main uncertainty is not the MoE path; it is exact and fast Gated DeltaNet
state handling across decode, chunked prefill, prefix reuse, and disk session
restore.

## Correctness gates

No tranche is promoted on plausible-looking text alone.

1. Preserve `make model-free-test`, `make cpu`, and
   `make build-isolation-test` on every tranche.
2. Add tokenizer golden vectors from the official Qwen tokenizer covering
   ASCII, Italian accents, CJK, whitespace, source code, special tokens, tools,
   and multi-turn messages.
3. Compare greedy tokens and top-logprob slices against official BF16
   Transformers and current llama.cpp references at positions 1, 2, 16, 128,
   and after a chunk boundary.
4. Compare recurrent convolution and DeltaNet state after single-token decode,
   full prefill, and at least two different chunk sizes.
5. Require resident and SSD-streaming paths to select the same tokens and match
   logits within a fixed numeric tolerance on the same quant.
6. Resume a saved multi-turn session and compare subsequent tokens/logits with
   an uninterrupted run.
7. Run canonical Qwen tool-call round trips, malformed-tool recovery, thinking
   on/off, and parallel request isolation through `ds4-server`.
8. Re-run DeepSeek Flash continuation, long-context, server, Metal-kernel, and
   before/after speed tests.  Qwen support may not regress the existing release
   path.

## Performance and small-Mac gates

Record machine, macOS, commit, backend, GGUF hash/recipe, context, power state,
memory pressure, swap deltas, cache size/hit rate, prefill, first-token latency,
and generation speed.

Required release measurements:

- resident A/B against current llama.cpp on the same 32/64 GiB Mac;
- forced SSD streaming on the same machine with bounded expert-cache sizes;
- a physical 16 GiB Apple Silicon Mac at 8,192 context, using cold and repeated
  warm 128-prompt + 64-generation-token runs;
- a 32,768-context run on at least 32 GiB;
- one multi-turn coding-agent session with tool calls and prefix reuse.

Release thresholds:

- no new swapout during the bounded 16 GiB run;
- lockable expert cache or a fail-closed startup error;
- resident generation at least 85% of llama.cpp on the same quant and prompt;
- warm SSD generation at least 3.0 t/s on the tested 16 GiB machine;
- warm first token no slower than 5 seconds for the bounded 8K test;
- no statistically meaningful DeepSeek Flash speed regression.

If the 16 GiB threshold fails after the cache, overlap, and Q4 expert paths are
profiled, do not lower the bar by relabeling an IQ2 model as the same quality
tier.  Report the measured blocker and re-evaluate Qwen3-30B-A3B or the smallest
future open Qwen3.7 MoE instead.

## Post-implementation evidence record

Recorded on 2026-07-14 after the preregistered implementation began.  This
section does not retroactively change the target or lower any release gate
above.  It records what the first experimental runtime now proves and what it
still does not prove.

### Implemented support boundary

The live Metal path supports only the normalized text-only
`Qwen3.6-35B-A3B-ds4-Q4_K_S.gguf`, architecture `qwen35moe`, with the blessed
733-tensor inventory and no MTP or vision payload.  It does not claim
compatibility with Qwen3.7, a separate Coder model, or arbitrary community
Qwen GGUFs.

The path is fail-closed unless all of these are explicit:

- an Apple Metal build and `--metal`;
- `DS4_QWEN_EXPERIMENTAL_METAL=1`;
- SSD residency through `--ssd-streaming`;
- `--power 100`;
- the exact validated metadata and tensor layout.

Resident Qwen Metal inference is not enabled by this experiment.  The scalar
CPU reference remains a separate model-backed validation path behind
`DS4_QWEN_EXPERIMENTAL_CPU=1`.

Each routed expert occupies 1,769,472 bytes.  The cache policy now has two
named tiers:

| Tier | Experts | Bytes | Meaning |
| --- | ---: | ---: | --- |
| Safe floor | 321 | 568,000,512 (0.529 GiB) | 40 x top-8 working set plus one in-flight safety slot |
| Recommended start | 640 | 1,132,462,080 (1.055 GiB) | two complete routes; anti-thrashing warning clears |

Requests below 321 are rejected.  An explicit 640-expert request can also be
rejected when the host-memory planner cannot fit it safely under current
pressure; it is a recommended starting tier, not a promise for every host.

### Reproduction commands

The one-token gate uses byte-exact rendered input with no trailing newline:

```sh
MODEL=/absolute/path/to/Qwen3.6-35B-A3B-ds4-Q4_K_S.gguf
OUT=/tmp/qwen36-metal-one-token
mkdir -p "$OUT"
printf '%s' '<|im_start|>' > "$OUT/prompt.txt"

DS4_QWEN_EXPERIMENTAL_METAL=1 \
DS4_METAL_MEMORY_REPORT=1 \
DS4_MOE_RECORD_SELECTED_IDS="$OUT/selected-ids.bin" \
  /usr/bin/time -l ./ds4 -m "$MODEL" \
    --metal --ssd-streaming --ssd-streaming-cold \
    --ssd-streaming-cache-experts 321 \
    --power 100 -c 2 \
    --dump-logits "$OUT/metal-logits.json" \
    --prompt-file "$OUT/prompt.txt" \
    > "$OUT/stdout.log" 2> "$OUT/stderr.log"
```

The bounded deterministic coding continuation uses the recommended cache tier:

```sh
MODEL=/absolute/path/to/Qwen3.6-35B-A3B-ds4-Q4_K_S.gguf
OUT=/tmp/qwen36-metal-coder-n96
mkdir -p "$OUT"

DS4_QWEN_EXPERIMENTAL_METAL=1 \
DS4_METAL_MEMORY_REPORT=1 \
DS4_MOE_RECORD_SELECTED_IDS="$OUT/selected-ids.bin" \
  /usr/bin/time -l ./ds4 -m "$MODEL" \
    --metal --ssd-streaming --ssd-streaming-cold \
    --ssd-streaming-cache-experts 640 \
    --power 100 -c 160 -n 96 -t 18 \
    --temp 0 --top-p 1 --min-p 0 --seed 1 --nothink \
    -p 'Scrivi solo codice Python: una funzione fibonacci(n) iterativa, con validazione per n negativo.' \
    > "$OUT/stdout.log" 2> "$OUT/stderr.log"
```

`tests/qwen/README.md` records the matching CPU-reference command, oracle
procedure, evidence hashes, and interpretation of the loader counters.

### Gates still open

The implementation is an alive and numerically close experimental path, not
the completed release preregistered above:

- all measurements are on an M5 Pro with 64 GiB; the physical 16 GiB pressure,
  swap, cold/warm, and 8K-context gates remain unrun;
- Qwen prefill is scalar (`prefill_cap=1`) and correctness-first;
- `--quality` and MTP are rejected;
- session payloads/snapshots and layer slices/distributed execution are not
  implemented;
- imatrix, expert profiles/hotlists, expert preload, directional steering, and
  non-routed pin profiles are not supported;
- resident/SSD equivalence, longer oracle continuations, disk restore,
  server/tool-call sessions, 8K/32K context, and DeepSeek before/after
  regressions remain required.

Do not infer 16 GiB readiness from the low measured Metal RSS on the 64 GiB
machine.  The preregistered physical-hardware and sustained-generation gates
remain the authority for that claim.
