# M5 Pro fork/upstream and GLM feature A/B — 2026-07-14

This note records the evidence behind the compact benchmark table in the root
README. It deliberately separates a direct fork/upstream comparison from an
isolated feature comparison.

> [!CAUTION]
> This is fresh single-host developer evidence, not a universal benchmark.
> The exact inference commands, tracked prompts, compact raw rows, hashes, and
> rejected-run rule are committed below. Full host telemetry remains local under
> `bench-logs/fork-vs-antirez-20260714/`, which is git-excluded.

## Host and test discipline

- MacBook Pro with Apple M5 Pro and 64 GiB unified memory.
- macOS 26.5.1 (`25F80`), arm64, internal 1 TB SSD, AC power.
- Metal backend and explicit SSD streaming.
- Runs were sequential. Geometric means use two retained repetitions per arm.
- Correctness was checked with frontier-logit or generated-output hashes.

## DeepSeek V4 Flash: direct upstream versus fork

Question: do the recent safety, AUTO/cache, telemetry, and teardown changes on
fork `main` regress the existing DeepSeek SSD-streaming path?

- Upstream: `antirez/ds4` `main` at `80ebbc3`.
- Fork: `andreaborio/ds4` `main` at `1523b26`.
- Model: DeepSeek V4 Flash IQ2XXS, 86,720,111,488 bytes
  (80.76 GiB), with Q2_K down projections and Q8 attention/shared experts/output.
- Workload: 128 prefill tokens, 256 generated tokens, context 32,768.
- Cache control: exactly 3,000 routed experts cached and 3,000 preloaded.
- Order: upstream, fork, fork, upstream (A/B/B/A).

Run the same command with the upstream and fork `ds4-bench` binaries, in the
order above. Change `OUT` for every leg:

```sh
BIN=/path/to/checked-out-build/metal-arm64/bin/ds4-bench
MODEL=/path/to/DeepSeek-V4-Flash-IQ2XXS-w2Q2K-AProjQ8-SExpQ8-OutQ8-chat-v2-imatrix.gguf
OUT=/tmp/ds4-ab-leg

"$BIN" --metal --ssd-streaming \
  --ssd-streaming-cache-experts 3000 \
  --ssd-streaming-preload-experts 3000 \
  -m "$MODEL" \
  --prompt-file tests/long_context_security_prompt.txt \
  --ctx-start 128 --ctx-max 128 --ctx-alloc 32768 \
  --gen-tokens 256 \
  --dump-frontier-logits-dir "$OUT.logits" \
  --csv "$OUT.csv"
```

Before each leg, verify AC power, no other `ds4`, `ds4-bench`, `ds4-server`, or
`llama-server` process, and capture `vm_stat`, `memory_pressure -Q`, and
`sysctl -n vm.swapusage`. The bounded runner in
[`../../speed-bench/run_m5_dsflash_arm.sh`](../../speed-bench/run_m5_dsflash_arm.sh)
implements those host-safety checks; the published arm above differs only by
using a fixed 3,000-expert cache/preload and 256 generated tokens.

| Arm | Prefill t/s | Decode t/s |
| --- | ---: | ---: |
| Upstream rep 1 | 19.88 | 12.55 |
| Fork rep 1 | 20.54 | 12.53 |
| Fork rep 2 | 20.97 | 12.63 |
| Upstream rep 2 | 21.49 | 12.72 |
| **Upstream geomean** | **20.6693** | **12.6347** |
| **Fork geomean** | **20.7539** | **12.5799** |
| **Fork delta** | **+0.41%** | **-0.43%** |

All four frontier-logit files have the same SHA-256:

```text
476a31661beb5beecd4d1b5e4bd48611bf59464836843a15f43a7c6aaa4eb0ae
```

The first upstream leg recorded 36 additional global swapout pages (less than
1 MiB at the 16 KiB host page size); the other three legs recorded zero. This
does not reverse the throughput verdict, but it prevents presenting the run as
strict zero-swap proof.

**Verdict:** performance parity. The fork is not faster than upstream on this
DeepSeek workload, and it does not show a meaningful regression either.

## GLM 5.2: isolated indexed-prefill comparison

Question: how much does indexed-prefill preparation improve streamed GLM
prefill, and does it also improve decode?

A direct whole-binary comparison is not possible with the local artifact: the
pure `antirez/glm5.2` binary rejects the ds4-native GGUF because the required
`blk.3.indexer.attn_q_b.weight` tensor is absent from its expected layout.
Therefore both arms use the same compatible fork build, `4eab362`, with only
indexed-prefill preparation toggled off/on.

- Model: GLM 5.2 ds4-native GGUF, 262,147,189,920 bytes (244.14 GiB).
- Workload: 288 rendered prompt tokens and 16 generated tokens, context 32,768.
- SSD settings: zero full-resident layers, 528 cached experts.
- Common profile: router-ahead advisory, lookahead 1, expert readahead off.

Run OFF/ON/OFF/ON, one process at a time. The measured prompt ended in one
literal space with no final newline. The tracked source avoids invisible
trailing whitespace; the `perl` command reconstructs the measured 1,300-byte
file, which renders to 288 input tokens with this build:

```sh
MODEL=/path/to/glm52-ds4-native-64g.gguf
PROMPT_SOURCE=docs/benchmarks/prompts/glm-prefill-288.txt
PROMPT=/tmp/glm-prefill-288-exact.txt
perl -0pe 's/\n\z/ /' "$PROMPT_SOURCE" > "$PROMPT"

# Indexed-prefill preparation OFF.
env DS4_GLM_ROUTER_AHEAD_PREFETCH=1 \
    DS4_METAL_DISABLE_STREAMING_EXPERT_READAHEAD=1 \
  ./ds4 -m "$MODEL" --ssd-streaming \
    --ssd-streaming-cache-experts 528 \
    --ssd-streaming-full-layers 0 \
    --prompt-file "$PROMPT" -n 16 --temp 0

# Indexed-prefill preparation ON.
env DS4_GLM_ROUTER_AHEAD_PREFETCH=1 \
    DS4_METAL_DISABLE_STREAMING_EXPERT_READAHEAD=1 \
    DS4_METAL_ENABLE_GLM_INDEXED_PREFILL_PREPARE=1 \
  ./ds4 -m "$MODEL" --ssd-streaming \
    --ssd-streaming-cache-experts 528 \
    --ssd-streaming-full-layers 0 \
    --prompt-file "$PROMPT" -n 16 --temp 0
```

The reconstructed prompt SHA-256 is
`8370b23334333501f547cc398225149c246e4523be24b53bf84a1baa8a1fa970`.

| Arm | Prefill t/s | Decode t/s |
| --- | ---: | ---: |
| Prepare off rep 1 | 3.94 | 0.99 |
| Prepare on rep 1 | 9.49 | 0.95 |
| Prepare off rep 2 | 3.64 | 0.93 |
| Prepare on rep 2, rerun | 8.83 | 0.88 |
| **Off geomean** | **3.7870** | **0.9595** |
| **On geomean** | **9.1541** | **0.9143** |
| **On/off** | **2.417× (+141.7%)** | **-4.7%** |

All four retained outputs have the same SHA-256:

```text
43ad5f6400f1c3ba9399ced8be6cf28c607139284f5153138112bb9e5ab86993
```

The original second `on` leg ran during unrelated Qwen oracle activity and
dropped to 3.19 prefill / 0.36 decode t/s. It was rejected as concurrent-load
contamination and rerun only after the competing process was gone. The retained
rerun is reported above; the rejected value is disclosed here rather than
silently removed.

**Verdict:** the feature is a large, correctness-neutral prefill improvement on
this short prompt. It is not a decode improvement. This agrees with the
independent July 10 campaign in
[`../../SSD_STREAMING_VERIFICATION.md`](../../SSD_STREAMING_VERIFICATION.md),
which measured roughly 2.5× on the same short-prompt class and 1.6–2.0× across
the longer sweep reported in upstream PR #528.

## What these results do not claim

- They do not claim that this fork is generally faster than `antirez/ds4`.
- They do not compare DeepSeek t/s with GLM t/s; the models and workloads differ.
- They do not establish fork-specific gains on CUDA/Blackwell or ROCm/Strix Halo.
- They do not establish sustained throughput on a 16 GiB Mac.
- They do not show a GLM decode win.
- They do not make Qwen Metal or SSD streaming release-ready.

Future promoted benchmark rows should additionally commit the full
machine-state capture and raw stderr rather than retaining them only in the
local excluded log directory.
